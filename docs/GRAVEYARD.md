# GRAVEYARD — Dead Ends Registry

**Audience: AI assistants (Claude, Codex, any model) and humans working on this repo.**
Every entry below is an approach that was actually tried and killed, with the root cause of death. Days of work are buried here — do not dig them up by accident.

## Rules of this file

1. **Before building anything new** in these domains — live streaming/mixing, pitch shifting, ensemble/choir sound, female timbre, transcription, per-voice timbre, wearable hardware — search this file first. If your idea matches an entry, do NOT re-run it; read *Instead* and attack the recorded root cause.
2. **When an approach dies, register it here BEFORE moving on.** Format: Tried / Died because / Evidence / Instead. A one-line burial saves the next model a day of excavation.
3. **Entries are never deleted.** A superseded direction gets a status note, not removal.
4. A verdict here is a **root-cause** conclusion, not "didn't work once". If you believe the premise has changed (new engine API, new model, GPU available), say so explicitly in your plan and cite what changed — that is the only legitimate way past an entry.

## Live engine / streaming

### G1. Mixing or splicing two engine output streams (all variants)
- **Tried:** dual-stream crossfade (scored 3/10 by ear), 20 ms fade splice (blurred), energy-valley splice + 5 ms fade (blurred). ~12 prototype iterations.
- **Died because:** the Beatrice waveform generator's phase free-runs per stream. Two streams of the *same* voice are phase-incoherent, so any crossfade combs/blurs. This is a property of the engine, not of the fade length.
- **Evidence:** 2026-07-05 session; prototypes `feed_ab.py` v0–v11 (scratchpad); the worklog of 2026-07-05 (development repository).
- **Instead:** one stateful stream per voice, change pitch *within* the stream via glide (see FINDINGS F2).

### G2. vcclient-style chunk + context re-feed applied to dynamic harmony
- **Tried:** re-feeding context audio per chunk (how vcclient batches) while the harmony shift changes.
- **Died because:** re-feeding interrupts the stateful stream → ~10 Hz tremolo on the output.
- **Evidence:** 2026-07-05 diagnosis (same worklog as G1). vcclient gets away with it because its pitch shift is *static*.
- **Instead:** FINDINGS F2 (glide inside one stateful stream).

### G3. "Two factories": neural engine at fixed pitch + external real-time DSP pitch shifter
- **Tried:** delay-line 2-tap-crossfade real-time shifter applied after the engine.
- **Died because:** the shifter itself sounds bad (warble/metallic) even offline.
- **Evidence:** commit `121466c2` (docs: Task 6 ATTEMPTED, dead end), 2026-07-05.
- **Instead:** FINDINGS F2. The 7→9 quality gap needs a feature-domain custom engine binding (post-viva project).

### G4. Jumping `set_pitch_shift_semitone` directly to the new target
- **Tried:** setting the new shift value in one step on note changes.
- **Died because:** every *change* (regardless of size) scrapes the engine's internal state; a melody makes ~18 changes in 8 s → constant instability ("scrape").
- **Evidence:** 2026-07-05; decompiled vcclient 2.2.2 confirms it glides via tiny `set_config` cent-steps and never jumps.
- **Instead:** glide 3–6 ¢ per 10 ms hop + 80 ms debounce (FINDINGS F2). Note the rc0 binding quantises pitch with a ~5–10 ¢ deadzone, so micro-detune via this API is a no-op (see G8).

### G5. Skipping inference for toggled-off voices to save CPU
- **Tried:** `if not voice.on: continue` in the voice loop.
- **Died because:** a cold converter resumed with ~35 ms of zeros per re-enable → the "choppy toggle" symptom. 39 exact 35 ms digital-silence gaps were measured in a recorded stem; pump underruns ≈ 2 and PortAudio overflows = 0, proving the earlier buffer/underrun theory wrong.
- **Evidence:** 2026-06-22; offline A/B: skip-mode 27.0 % spurious zero-fill vs always-run 0.1 %.
- **Instead:** always run inference for every live voice (keep warm), gate only at the mix sum. Cost: RTF no longer shrinks with voices off (~0.375 for 3 parts — acceptable). Offline render may still skip.

### G6. Real-time input-side pre-shift (+12 into the model) for female timbre
- **Tried:** granular real-time pitch shifter before the engine (`server/female_timbre_test.py`).
- **Died because:** granular shifting destroys phoneme content; +12 clips and feeds garbage to the model. Output-side TUNE (octave-up) already achieves the same goal.
- **Evidence:** 2026-06-21 by-ear.
- **Instead:** output-side TUNE / per-voice octave; offline kNN-VC for genuine female timbre (FINDINGS F5).

### G7. Blaming device-switch timbre collapse on "input overflow"
- **Tried:** treating the post-device-switch collapse (all voices turn male) as an input/clock corruption problem.
- **Died because:** a clean independent mic stream still collapsed. Real cause: the UI's `controlState()` sent `voices` without the `model` field; `bridge.set_control` did a whole-dict `update()`; `_restart_engine` then rebuilt every voice on the default `"tenor"` model.
- **Evidence:** 2026-06-22; fix in `app/bridge.py set_control`.
- **Instead:** when live timbre changes inexplicably, check control-state completeness across restarts *first* (DEBUG_PLAYBOOK), not audio-clock theories.

### G8. Neural-API micro-detune for ensemble spread
- **Tried:** small per-voice detunes (±5–15 ¢) through the engine pitch API.
- **Died because:** the rc0 binding quantises pitch with a ~5–10 ¢ deadzone — small detunes are silently dropped.
- **Evidence:** 2026-07-04/05 sessions.
- **Instead:** do decorrelation offline in the signal domain (WORLD recipe, FINDINGS F3).

## Timbre / ensemble

### G9. "Distinct speakers ⇒ clean ensemble" (DISPROVEN)
- **Tried:** giving each of 6 copies a different `target_speaker` expecting a choir.
- **Died because:** time-aligned copies fuse into "one person" regardless of timbre. Timbre difference is neither sufficient nor necessary for ensemble.
- **Evidence:** 2026-06-22 by-ear; corrected 2026-07-04 by the decorrelation work.
- **Instead:** pitch + timing decorrelation, independent vibrato, stereo pan (FINDINGS F3). Speaker variety is optional seasoning.

### G10. Per-voice formant spread on one model (Bass −1 … Sop +1)
- **Tried:** spreading `formant_shift` across parts to differentiate the "choir of one".
- **Died because:** with tight voicing on a single model, spreads of 0 / 1.0 / 1.6 were indistinguishable in the mix (user A/B). Single-model timbre is inherently homogeneous; formant can't fix it.
- **Evidence:** 2026-06-25, feature reverted same day.
- **Instead:** real timbre diversity needs different models/speakers (which re-opens the electronic-timbre problem) or offline kNN-VC (FINDINGS F5).

### G11. Live stereo "ensemble/spread" rework
- **Tried:** live stereo widening of the parts (2026-06-21).
- **Died because:** Alto sounded wrong; abandoned, UI controls removed.
- **Instead:** stereo belongs in the offline decorrelation recipe (FINDINGS F3), not in the live path.

### G12. kNN-VC soprano via pitch-shifted input
- **Tried:** (a) librosa phase-vocoder +12 → formants shift too → chipmunk, worse WavLM matching; (b) WORLD/pyworld formant-preserving shift (f0×2, envelope kept) → input sounds natural but soprano output still bad.
- **Died because:** (b) failing proves the root cause is kNN-VC/WavLM being out-of-distribution at high register — not shift quality.
- **Evidence:** 2026-06-26.
- **Instead:** in this arranger Sop carries the melody in the *male* register, so Sop simply uses the **alto reference pool** — it was a register-mismatch problem, not a high-note problem. See FINDINGS F5.

### G13. Expecting Beatrice male→female conversion to sound female
- **Tried:** male input through the trained female / satb2 female speaker expecting a female voice.
- **Died because:** Beatrice preserves substantial source vocal-tract character; male→female yields "neutral", not female. This is documented source-speaker leakage (arXiv 2504.15822), not a bug in this repo, and cannot be fixed at the mix level.
- **Evidence:** 2026-06-21 by-ear; literature survey 2026-06-24.
- **Instead:** (i) push output pitch ≥ ~A4 and female timbre emerges (use TUNE/octave); (ii) offline kNN-VC render (FINDINGS F5); (iii) convincing *live* female needs GPU inference — out of scope on CPU.
- **⚠ 2026-08-14 — the verdict stands, the 07-22 numbers below do NOT. Do not cite them.** Re-measured through `260811_bt/render_bt.py` (same take, same satb2 model, only `target_speaker` changed), at **both** registers because the 07-22 run used `female_timbre_test.py`, whose default is `PITCH=0.0` — i.e. the male register this very entry says female timbre cannot appear in:
  - 0 semitones: correlation **0.575**, centroid **980 vs 773 Hz = 21.1 %** (07-22 recorded 0.955 / 2 %)
  - +12 semitones: correlation **0.673**, centroid **1215 vs 955 Hz = 21.4 %**, log-spectral distance 8.82 dB
  - Whole-file centroid (no frame gating) gives 1051 vs 867 = 17.5 % — the discrepancy is not a framing artefact.
  The two speakers differ ~10× more than recorded. Most likely the 07-22 measurement was taken through a path where the speaker never actually switched — this entry itself documents that that control chain had `except: pass` swallowing failures and was a silent no-op on single-speaker models. **Lesson: a number measured through a path with a known silent-failure mode is not evidence; re-measure through a path that has been proven to apply the setting.**
  **By ear, 2026-08-14, loudness-aligned A/B at +12 (`ear/AB_satb2_spk0_vs_spk1_up12.wav`): both female.** So the conclusion holds by ear (the speaker index is not a voice-type control) even though the supporting metric was wrong, and metric-vs-ear conflicts still resolve to the ear. Live SATB got solved another way — see FINDINGS **F23** (two models coexist at `--blocksize 960`), which removes the reason anyone wanted joint multi-speaker training in the first place.
- **Measured 2026-07-22 (satb2, same take through spk0 vs spk1) — SUPERSEDED, see the warning above:** correlation **0.955**, difference RMS 30 % of signal, spectral centroid **904 vs 886 Hz** — a 2 % shift. The switch *works*; it is simply not a gender change. **Consequence: the UI's F/M control was removed** (`3c90803b`) — it claimed male/female, delivered a faint variant, was a silent no-op on the six single-speaker models (`get_num_speakers() == 1`), and its failure was swallowed by `except: pass`. Four layers of dishonesty stacked into "is this a bug?". Engine-side `--speaker*` launch args stay.

## Transcription (studio)

### G14. CREPE (and madmom)
- **Tried:** CREPE for f0 (separate ~5 GB `vcclient-crepe` conda env with TF/numpy2); madmom for onsets.
- **Died because:** SwiftF0 (MIT) matched CREPE's low-register accuracy without octave jumps, runs in-process, no TF. madmom won't compile on numpy2 at all. Retired a second time when the heuristic onset stack itself was replaced (G15).
- **Evidence:** commit `319b1fe6` (SwiftF0 swap); `server/transcribe_crepe.py` removed; `conda env remove -n vcclient-crepe` is safe.
- **Instead:** `_hmm_melody` global Viterbi decode (default since `76d3e15f`), `_swiftf0_melody` heuristics as fallback.

### G15. Piling more onset/segmentation heuristics onto transcription
- **Tried:** rounds of heuristics — vowel-boundary MFCC splits, tuning-centre θ quantisation, leap-transit absorb, fry/crack trimming (commits `ed3b447a`, `78358e33`, `c5333588`, `4652f4bf`, `96a870dd`, `c8575fd0`).
- **Died because (ceiling declared 2026-07-06):** on the 10-take suite the remaining errors are *true input ambiguity* — same-pitch legato syllables with no energy/spectral cue, and notes sung on an x.5-semitone boundary that honestly quantise to either neighbour. No heuristic can decide these.
- **Instead:** the drag-to-edit editor is the designed fix for the residual. Do NOT add heuristic rounds; if transcription "looks wrong", first check whether it is one of these two ambiguity classes.

### G24. Offline arranger-rendered stimuli for the baseline listening test — 2026-07-22

- **Tried:** `eval/render_stimuli.py` → `studio_api.transcribe()` → `arranger.arrange_with_chords()` → render Beatrice + naive from the same score, as the A/B material for the viva-keystone listening test.
- **Died because — ONE sufficient reason, plus one hypothesis that is NOT established:**
  1. **(SUFFICIENT, no listening data needed) It does not represent the instrument.** The live app harmonises by fixed diatonic scale-steps (`SoloChoir.py`, `--free` adds causal chord inference); the studio arranger does chord inference + voice-leading + bloom + per-voice register tables. They are different instruments — testing one says nothing about the other. **This alone kills the route**; it is verifiable from the code and does not depend on anything below.
  2. **(HYPOTHESIS — NOT VERIFIED, corrected 2026-07-22 evening)** The original entry claimed the arranger's voicing "swamped the variable under test" and called it a root cause. That overstates the evidence. **What was actually measured:** soprano shifted **+15 … +17 semitones** on the 4 real takes; the two conditions are objectively different (correlation 0.27–0.41, naive's spectral centroid consistently +124–249 Hz — the phase-vocoder formant-shift fingerprint, so rendering did not fail); Harry scored **2/4** on a blind guess. **What was never measured:** that the register shift is *why* it was inaudible. The obvious control — re-render at a sane soprano register and blind-listen again — was never run; the route was abandoned instead.
- **The bigger hole the original entry missed: the test had no statistical power.** 4 binary trials, one listener. Under pure guessing, P(exactly 2/4) = **0.375** — the observed result is the single most likely outcome of a coin flip. A listener who could genuinely hear the difference 75 % of the time still scores 2/4 about **21 %** of the time. Worse, **the design could not have produced a significant positive result under any outcome**: even a perfect 4/4 gives a one-tailed p of **0.0625**. So **2/4 supports no conclusion at all** — not "the chipmunk masked it", not "the difference is inaudible", not anything. The honest reading is *"this test returned no interpretable result"*.
- **Alternatives never ruled out** (any of these could equally explain 2/4): the Beatrice-vs-naive difference may simply be hard to hear **inside a 4-part mix** (it was audible in earlier solo comparisons — a mix masks); procedure/blinding effects; or plain lack of power.
- **Carry-forward for RQ1 (this is why the correction matters).** RQ1 ("must the harmony sound like a human voice?") is the *same comparison*, just delivered live. If the difference is hard to hear in a mix, the live A/B fails the same way — and repeating "one listener, four trials" on 07-27 will again yield nothing interpretable. **Before running it, fix the trial count and n, and decide how to avoid mix masking.** A cheap prior check exists with material already on disk: `eval/stimuli_260721_private/_render_*/` holds **per-part stems for both conditions** (`studio_alto.wav` vs `naive_alto.wav` …), so a single-part A/B tests audibility with no arrangement and no mix confound, without re-rendering anything. **Do not delete those directories** until that question is settled. They are **untracked and deliberately not committed** (65 MB of wav; and `_private/KEY.csv` is the unblinding map — the generating script warns "never serve it", so it must not ride along in a pushed repo).
- **Also found:** transcription octave errors survive into the stimuli (phrase 1 had two isolated MIDI-82 notes, 34 semitones above the median) — `render_stimuli.py` transcribes internally and has **no injection point for a corrected score**, so the "EDIT the score" step in the plan has no implementation.
- **Instead:** live A/B inside solo_min — `--naive` swaps only the per-voice timbre generation, keeping f0, the diatonic decision and the harmony identical (`e00340b6`, FINDINGS F13). Supervisor-sanctioned direction (Matthew meeting: build a real-time shifter to compare against). The baseline algorithm is the author's own prior instrument, `yvwHY/Harmonizing` (Tone.js `PitchShift`), so it is a citable tool rather than an ad-hoc straw man.

### G23. `--voice-delay` Tier-1 live canon (part separation Tier 1, "singing a round with your past self") — by-ear FAIL 2026-07-19

### G22. Nape pivot as a separate hinge (through-pin at tube ends / whole-yoke rotation about (0,146,−31.5)) — 2026-07-10
- **Tried (4 versions in one day):** rectangular blocks → ⌀18 hinge barrel + ⌀3 through-pin (press-fit, then bayonet front-entry) → boss-and-fork "eyeglass hinge". All CAD-verified individually, all killed by two facts in combination:
  1. **The pin corridor is owned by the wire.** The nape tubes' lower ends pass 1.2 mm from the pivot axis, so any axial member (pin, screw, pilot hole) at x ±(8.5..11.65) collides with them. Trimming the wire to clear it is FORBIDDEN (Harry's standing rule 2026-07-10: the wire is never cut to accommodate a part — parts accommodate the wire).
  2. **Whole-yoke rotation about the tube-end axis cannot don.** In the real donning direction (chest panel lifts over the face — the direction whose ear corridor was tuned 07-09) the collar/sleeve hits the nape tubes after only ~20° (tube "spoke" sits at θ≈138°, collar rest at 164° → 26° margin). The clear direction (+130°) sweeps the panel through the wearer's torso. The 07-09 assembly articulation "verified" this joint only because Fusion joints do no collision checking, and only arms-vs-ears was ever swept.
- **Instead (v4, SHIPPED):** **the collar's own straight rear section IS the axis** — the ⌀3 wire rotates inside a printed ⌀3.3 bearing channel (`pivot_mount`, single fixed part, no metal pin, no printed joint). Collar sweep radius = 0, so the tube collision vanishes identically; panel arc unchanged. Do not reintroduce a discrete nape hinge without re-reading this entry.

### G25. "Narrow every brass channel on the whole build to 0.05 mm clearance per side" (2026-07-21) — FAILED in print 2026-07-22
- **Tried:** to remove the slack, every channel taking a 3.0 mm brass rod was narrowed **uniformly** to 0.05 mm of clearance per side (`band_clamp`'s headband tunnel and **both centre-post channels, 4.3 to 3.1**, `pivot_mount` 3.8 to 3.1, `door_col` 3.8 to 3.2, `wo4_cup` 3.6 to 3.2, the J-hook seat 3.3 to 3.1). `measureMinimumDistance` verified 0.0500 on every one in CAD, and the numbers looked perfect.
- **Died because:** once printed, **the two centre-post channels of `band_clamp` would not accept the rod**, while the rest did. The difference is not the bore, since both those channels and `pivot_mount` are 3.10 mm at 0.05 per side, but **whether the channel is curved**: the bounding box of faces `f1/f2` of the centre-post channel is 3.100 x **5.474** x 20.000, where a straight channel would have a Y extent equal to the bore, so the post axis wanders **2.374 mm** sideways over band_clamp's 20 mm height, while `pivot_mount` is **a straight hole** on a single cylindrical face. The centre post was **cold-bent by hand** on 2026-07-20 (worklog 07-20 section D), and a hand-bent rod cannot match a CAD spline to 0.05 mm over 2.3 mm of wander. **The old 4.3 mm value, 0.65 per side, existed precisely to absorb that error, and narrowing everything uniformly removed it.**
- **It was not thermal shrinkage.** That was the first attribution on both sides; PLA's linear shrinkage of 0.3-0.5% works out to **0.012 mm** on a 3.1 mm bore, an order of magnitude below the layer height. **Work out the order of magnitude before attributing a cause.**
- **Evidence:** worklog 2026-07-22 §G；`prints/260722_prints/README.md`。
- **Instead:** **clearance follows the shape of the channel and cannot be one number for the whole build.** A straight hole works at 0.05-0.10 per side; **a curved channel must be figured separately** (this batch tries 3.30 mm, 0.15 per side). If 3.30 still will not pass, the hand-bending error exceeds 0.15 mm and **the next version turns the centre-post channel into a C-shaped throat that clips in from the side** — a trick already proved on `band_clamp`'s headband seat and the `vu1_panel` clamp — rather than opening it further until it is loose. Do not accept "one clearance for the whole build" at face value again.

## The harmony parts, harmony_brain (the new line from 2026-07-22)

### G26. A granular dual-tap pitch shifter as the parts' voice (ShiftVoice) — FAILED on a real voice 2026-07-22
- **Tried:** whammy-style dual-tap pitch shifting over a ring buffer (`260722_harmony_brain/live.py` ShiftVoice) plus a frozen sustain and auto-octave range folding. It passed every acceptance test on a synthetic sawtooth: shift accuracy 46.0/44.1, the frozen sustain, and 9.2x rising to 226x real time.
- **Died because:** three rounds by ear on a real voice all failed: heavy wobble, no intonation, muddy in the low register, and it did not sound like the person. Measurement convicted it: 52 breaks in 56 s, an f0 std of 0.65 semitones within a segment where a steady human voice gives 0.1-0.3, 1-8 Hz amplitude artefacts holding 59% of the envelope energy — the sweeping beat inherent to a dual-tap crossfade — and the ratio being tied to the live f0, so tracking flicker passed straight to the output.
- **Lesson, paid for: passing on a synthetic test signal is not passing on a real voice. The acceptance signal for a voice pipeline must be a real recording** (the take.wav stems and the offline replay loop were built after this).
- **Instead:** WORLD analysis and resynthesis; the batch version was the first whose quality was accepted.

### G27. vcclient external control as the live pitch channel (REST convert_chunk and slot PUT) — 2026-07-22
- **Tried:** starting `model/VC/dist` headless on port 18000; reverse-engineering the convert_chunk format (**16k in, 48k out, hop 160**, numbers still worth reusing); and a full-slot PUT of `pitch_shifts[dst_id]` (a partial field PUT has no effect; the whole object is required).

### G34. Distinguishing feedback in the energy domain from a single microphone (an envelope gate) — measurement FAIL 2026-08-10
- **Tried:** the aim was to separate the singer's direct sound from the parts coming back through the room without changing the wiring, so the model would not consume the parts' f0 (the same mechanism as G33b, reappearing in the streaming architecture). The method: since the signal `y` sent to the speakers is known to the sample, estimate the coupling gain k and the playback delay d, and treat `mic_env < thr * k * angel_env[t-d]` as feedback and withhold it from the model. The reasoning: on 2026-08-09 section N the envelope correlation measured r = +0.950 while the coherence was only 0.0133, so **what two clocks destroy is the phase and not the envelope**, and a negative verdict on phase-level echo cancellation does not imply that envelope-level discrimination is impossible. Artefact: `harmony/scratchpad/fb_duck_probe.py`.
- **Died because:** **structurally, not for want of tuning.** The loop is `angel(t) = G * mic(t)`, the system output proportional to its input, with G measured constant in diag17 (0.97:1 whether or not they are singing), while `mic(t) = direct(t) + k * angel(t-d)`. **The envelope of the whole loop is therefore self-similar and any mic-to-parts energy ratio tends to a constant.** Evidence: sweeping the delay from 0 to 697 ms made the separation **rise monotonically with no peak**, that is, no physical feedback path can be found and it is only the trivial effect that a longer delay correlates less; the best separation was a mere 1.68x, and a threshold sweep blocking 68% of feedback cost **26% of real singing killed by mistake**. A lesson on the side: `dmp["mic"]` and `dmp["out"]` are appended inside the same `step()` (`spike_stream6.py:1020-1021`), so the parts in the dump are on **the timeline at which they were produced**, not the one on which the speakers played them, and cross-correlating them directly gives the false result of a 0 ms delay at r = 0.864, which is the causal correlation of input driving output.
- **Instead:** change dimension rather than parameters, to information outside energy. CPP was tried and also died (see G35). The real next step is **to record clean calibration material first**, 30-60 s with the singer completely silent while the parts play through the speakers, which is the only way to obtain k, d and a feedback spectrum uncontaminated by direct sound. **Conditions for reopening:** once the microphone and the output share a clock, on one interface or an aggregate device with drift correction, phase-level echo cancellation deserves a retest anyway (`scratchpad/aec_probe.py` is kept), and this energy-domain approximation would then be unnecessary.
- **Update 2026-08-16, retested under the bank_live architecture; the verdict stands but the cause must be narrowed:** the structural cause given here, that the loop `angel = G * mic` is self-similar so the energy ratio is constant, **holds only for a live converting carrier**. bank_live's `y` is sampled playback from the banks (`bank_live.py:1864`), so the output is not a function of the microphone and that causal edge does not exist. The retest bears this out: after detrending, **the delay sweep has a peak (279 ms, r = +0.249)**, the negative-delay side correlates cleanly negatively, and the median separation is **6.76x** against the 1.68x recorded here. **It is still not enough to gate on**, and the reason is **not** poor calibration: the prescription written in the correction to this entry and G35, recording clean calibration material separately, had in fact already been done on 2026-08-10 (`CALIB_*`), and it showed the coupling to be flat (k(f) varying 3.1 dB), calibratable (-17.5 dB) and consistent with the blind estimate. The real weakness is **what the residual means**: using the calibrated k, the microphone with the singer silent still sits **+2.7 dB above the predicted feedback at the median**, so the microphone contains **non-feedback energy of the same order as the feedback** — breath, breathy consonants, movement, the room. The best threshold therefore mistakes feedback for singing **36.6%** of the time by definition and not through measurement error, and that is no better than the camera gate already condemned, which false-triggered 20-35% of the time with the mouth closed. See **FINDINGS F26** and the script `scratchpad/bank_fb_envcorr.py`. **This entry stays condemned for the streaming architecture**; under bank_live it is "not condemned but insufficiently discriminating", and the condition for reopening is now **a change of dimension**, information that can separate voiced singing from breath and movement, rather than calibrating the same energy ratio more precisely.

### G35. CPP as a feature separating a single note from a three-part chord for feedback discrimination — measurement FAIL 2026-08-10
- **Tried:** following G34's change of dimension. The reason for the feature came from the failure attribution of 2026-08-09 section N itself: "parselmouth is a monophonic tracker and HuBERT was trained on a single singer, so feeding them a three-part chord is out of distribution." That out-of-distribution property is the discriminating feature: **the singer sings one note, a single sharp peak in the cepstrum, while the parts coming back are a three-part chord and the peak is flattened.** Chordality does not scale with level, so in principle it survives the self-similarity of the loop. Artefact: `harmony/scratchpad/fb_spec_probe.py`, a 93 ms window over quefrencies of 70-400 Hz.
- **Died because:** the numbers look good on the surface — a best threshold of CPP = 0.13 dB at **88.9%** accuracy, against a baseline of 70.0% for always guessing "singing", catching 96.9% of real singing and blocking 70.4% of feedback — but **it is only a proxy for level**: CPP correlates with log RMS at **r = +0.602**, and once the overlapping RMS region is binned by level, the CPP difference at equal level is only **+0.027 dB** (feedback 0.145 against real singing 0.172). Since it merely restates the level, it adds nothing over the level criterion already in `bridge_feed`, and that criterion has already been defeated by feedback holding it open.
- **Instead:** as in G34, **the bottleneck is the material, not the feature.** The "not singing" ground truth in diag17 was itself cut by energy quantiles, so the two groups differ tenfold in RMS and barely overlap, which entangles every feature with energy and makes them impossible to disentangle. In principle this material cannot decide the fate of any discriminator. > **Correction to G34 and G35, made the same day (the evening of 2026-08-10, once the calibration material was in hand):** both verdicts stand, but **the arguments must be separated.** G34's cause, that the loop `angel = G * mic` is self-similar so the energy ratio is constant, depends on no ground truth and **still holds**. ### G36. Signal-level post-processing of the noise at phrase boundaries (three input treatments plus two output dynamics) — four by-ear failures and a red metric, 2026-08-10
- **Tried:** once the model layer was opened up, copy-synthesis first cleared the vocoder (a real mel through NSF-HiFiGAN was judged clean by ear), which pinned the problem to the mel generation side. The whispering quality was briefly attributed to rubbish in the input gaps, from a "silence the gaps" experiment, but **that was overturned the same day**: the report in that round was "it is not the breathy whispering, there is noise at both the start and the end", a correction of the description rather than a change in the report; the phenomenon does not vary with the material (clean30, different material, has the same inhaled sound at the start); and all five ways of cleaning the input had no effect, so it is not a problem with the material. The main phenomenon was boundary rendering noise from the start, which is what this entry is about. Bleed does exist, since it was heard in copy-synthesis, but its audible contribution is unproven. Five approaches were tried on the remaining noise at the start and end of a phrase: (1) digital silence in the gaps (gated); (2) replacing the gaps with a looped room noise floor (cn); (3) breath suppression plus a cosine attack ramp and a 150 ms release (v3); (4) an input-keyed downward expander (v4); (5) level-decoupled rendering (vd and vd2: clamp the vol condition so the voice never enters the low-level region, then multiply the real envelope back after rendering). Artefacts: `scratchpad/canon_take17_{gated,cn,v2,v3,vd}.py`, `boundary_metric.py` and `boundary_forensics.py`.
- **Died because:** the root cause is that **the voice's output signal-to-noise ratio collapses in the low-level region** (measured back at v27: as the level falls the harmonics drop 5.5 times while the noise drops only 1.5, and a time-frequency post-mortem at 37.1 s showed a 60 ms input ramp smeared by the voice into about 200 ms of full-band haze). Entering and leaving a phrase must pass through the low-level region, so **signal-level processing can only change the shape of the haze and cannot remove the illness**: a slower ramp makes the haze longer; a faster ramp or an expander produces abrupt gain changes ("there is more of it"); looped noise floor is a periodic false signal; and vd's fast attack gives a 40 ms step of 33 dB against 25 in the original, the same cause as v4's death, caught by the metric and never sent to the ear. **Two methodological lessons:** (1) a median trajectory washes out occasional bursts, which decouples the ruler from the ear, so each event must be examined and compared against the input event by event — a consonant is a high-frequency burst by nature, and only "a burst in the output where there is none in the input" is noise; (2) an energy metric cannot hear an abrupt gain change, so smoothness, the short-window energy step, has to be measured alongside it. That ruler, added after v4 failed, successfully predicted that vd would fail too.
- **Instead:** the illness is in the model, so the cure is in the model: **level augmentation during retraining**, several copies of each clip at different gains so the voice learns to decouple timbre from level, or checking whether the 6.x training configuration already supports volume augmentation. A related target is the inherent +5 dB of breathiness at the onset, which input shaping cannot remove and which belongs to the same rendering character. **Live is unaffected by this case**: the bridge gate already does the same thing and no complaint was made about boundaries live, so this lives in the reference and answering-mode pipelines. **Conditions for reopening:** after a change of vocoder or a retrained voice, the measurement tools from these five approaches (boundary_metric and boundary_forensics) can be reused directly for acceptance.

### G37. A frozen noise grid as the cure for unstable pitch (v33 --noise-grid) — the hypothesis rejected by a controlled measurement, 2026-08-10
- **Tried:** in the single-part live round of 2026-08-10 all three voices were reported as unstable in pitch. Measured by component: the live parts deviate from the commanded f0 with an std of 31 cents and 12% of frames over 30, while the live tracking error is only 10 cents and the offline reference on the same voice only 9, so the fault is in the live rendering layer. The hypothesis was that reflow's independent randn per window (the lesson of 2026-08-08, "the same input gives a different result twice") makes one sustained note change pitch path every 244 ms. v33 implemented it with three layers of guarded parameters: `init_noise` in reflow.py, pass-through in vocoder.py, and `--noise-grid` in spike_stream6 with a fixed-seed noise bank of 16384 frames per part, looked up by absolute frame position. With the flag off, regime A is proved (re-rendering the reference with the same seed gave a max absolute difference of 0.0 across four files).
- **Died because (at the level of the hypothesis; the code is kept):** an overlapping-window control experiment (the same audio, two windows offset by 0.244 s each rendered once, measuring pitch agreement in the overlap) gave **ts85 2.2 cents off against 2.6 on, and ts35, where the noise is 65%, 2.1 off against 2.2 on, so the noise realisation does not drive the pitch at any operating point** — the ODE velocity field pulls different noise back onto the same pitch trajectory. **The real culprit was found the same night**: binning the absolute deviation by the slope of the commanded pitch gives 7.1 cents on flat passages, as accurate as the reference and matching the report that a sustained note holds as one line, and 74 cents on steep ones, implying a time misalignment of about 1.3 frames, **15 ms**. That is **the join machinery (SOLA and the phase vocoder) smearing the moment of a note change in time, plus the frozen grid permanently freezing the coarse early f0 estimate from the end of a window** — the reference estimates with full context and does not have this illness.
- **Instead:** the target moves to **the join and freezing layers at the moment of a note change**. Candidates: deferred freezing, rendering new frames first and freezing only after m mature blocks so the f0 estimate has more context, which requires a trade-off against the original reason v6 froze at all, to stop skipping; or a review of SOLA's behaviour over a note change. The `--noise-grid` code is kept, being harmless and proved regime A, but it does not solve this case by itself. **Methodology:** a mechanical hypothesis should be struck once with a minimal controlled experiment before implementation. Here 8 pairs of overlapping windows rejected it in 20 minutes and saved a round of live listening.

> **Addendum to G34 (2026-08-18, reopened by Harry and passed by ear):** the decision was that live should be triggerable by the microphone alone, which reopens the verdict of 2026-08-16. bank_live v43 implements `--mic-gate`, an energy-domain gate with authority moved from the camera to the microphone. The first version, carrying the CALIB values, failed on contact with the gate open 88.6% of the time; after tuning against the first session's dump (a threshold of -26 dBFS and a coupling of -13.5 measured on this machine that day) the second test was judged acceptable. F26's defining weakness, breath and movement being misread about 37% of the time, is not circumvented: raising the threshold simply brought the false opens down to a level the ear accepts, 9% in simulation. This entry's verdict for **the streaming architecture** is unchanged; under bank_live its status becomes "an energy-domain gate in live service". See the worklog for 2026-08-18.

### G38. A BLE HID keyboard button (Pico W on official MicroPython) — the firmware lacks pairing support, 2026-08-18
- **Tried:** moving the physical button to Bluetooth, after the decision "then Bluetooth it is". A complete BLE HID keyboard was written on the Pico W (HID service 0x1812, a report map, and bond keys persisted to flash), so a press sends a space and the Mac side needs no change at all. Artefact: the first version of `firmware/pico_led_button/main_ble.py`, recoverable from the git history.
- **Died because:** **the official rp2 MicroPython, measured at v1.28.0, is not built with pairing or bonding.** Every `ble.config(bond / le_secure / mitm / io)` raises `ValueError: unknown config param`, since `MICROPY_PY_BLUETOOTH_ENABLE_PAIRING_BONDING` is not enabled, while macOS requires encrypted pairing for an HID input device and will not accept one without a bond. CircuitPython on the same board, through HCI _bleio, likewise does not support bonding. Making it work would mean building custom firmware, which is not worth it before the viva.
- **Instead:** **a custom GATT notification service that needs no pairing** (the current version of the same `main_ble.py`): the Pico notifies `TAP n`, `respond_shell._ble_loop` receives it through bleak and calls `self.tap()`, which is the same path and the same running number as the UI space key. Measured end to end at 67 of 67 taps. **Conditions for reopening:** if the official firmware is ever built with pairing, or custom firmware becomes acceptable, the first HID version can be pulled straight back out of git.
