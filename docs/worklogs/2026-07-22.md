## C. `--naive` 基線落地（commit `e00340b6`）

`server/voice_changer/naive_shift.py` 新增 `GranularShifter`（延遲線兩抽頭、100 ms 視窗、等功率交叉淡入，參數對齊 Tone.PitchShift）。solo_min 保留 `process_frame` 照跑，只把**音訊**換掉——f0、調內和聲判斷、遙測兩邊完全相同，變量只有音色。移調量取引擎剛算好的 `_cur_shift`（滑音之後），連滑音行為都一致。

UI 送 `{"naive": bool}` 即時切換：`set_control` 會把任何存在於 args 的 key 自動 setattr，所以加了 `--naive` 引數之後**控制管線零改動**。

三個 bug 是在 Harry 實際唱著測的時候被抓出來的，數字都記在 FINDINGS **F13**：
1. **移調器沒保溫** → 冷啟動第一個 hop 輸出 RMS **0.0000**（保溫 0.2986）＝ 切換爆音。改成每個 hop 都跑。
2. **兩條分支每 hop 樣本數不一致**（240 vs 237/240）→ 交叉淡入會截掉 Beatrice 的輸出、naive 穩態下 cushion 漂移。加固定區塊緩衝，實測恆定 `{240}`。
3. **交叉淡入本身**：25 ms 等功率，最極端切換的單樣本跳變 **2.0 → 0.0037**。

**延遲量測**（我先前口頭說「約 100 ms」是錯的，被 Harry 的耳朵糾正後才去量）：實際起音延遲 **4–50 ms、平均 10–33 ms**，因為兩抽頭相差半視窗、永遠有一個在讀新資料。與引擎路徑同量級，RQ1 的延遲混淆比原先擔心的小。

## D. 順手修掉的既有 bug：按任何控制都爆音（同 commit）

Harry 反映「聲音相關的 UI 切換都會小爆音，而且之前就有」。診斷過程：
- log 顯示 **`input overflow` 37 次、`output underflow` 0 次** → 不是輸出掉音，是輸入樣本被丟掉。
- 在 bridge 層加計時 → **`set_control` 平均 12.2 ms（7.8–15.3），而 callback 週期是 10 ms** → 每按一次就餓死音訊執行緒。
- 原因：收到**任何**一個 key 都對**全部**聲部重跑 `configure_voice` ＋ `set_target_speaker`，即使按的是與聲部設定無關的靜音鍵。

修法（FINDINGS **F12**）：cheap-key 快速路徑 ＋ speaker 快取。**12.2 ms → 0.0–0.1 ms**，爆音消失。白名單的安全性是**驗證過的**：`configure_voice` 只讀 `free/glide/hysteresis/interval/key/minor/mode/smooth/steps`，白名單裡沒有任何一個。

## 教訓

1. **量測前不要下結論。** 今天兩次：「199 點干涉」（07-21，取樣誤判）與「約 100 ms 延遲」（推論，實際 10–33 ms）。兩次都是 Harry 或量測把我糾正回來。
2. **查 GRAVEYARD 要在動手前，不是在重新發現之後。** F/M 那條 G13 已經寫得很清楚。
3. **GRAVEYARD 是給我用的，不是用來擋使用者。** 用 G3 去質疑指導教授定的方向是誤用。
4. **靜默失敗比壞掉更糟。** `except: pass` ＋ 樂觀的按鈕標籤 ＝ 使用者花時間追不存在的 bug。
5. **「印不出來」先問是哪一種失敗，再開始找原因。**（§G）三次失敗我都先跳到幾何：第一次其實是切片設定、第二次是選到 `._` 影子檔、第三次是檔案截斷。分流問題（螢幕顯示什麼？停在多高？有沒有支撐材？）比任何分析都便宜。
6. **「熱縮」「太緊」這種歸因要先算數量級。** PLA 收縮率換算到 ⌀3.1 只有 0.012 mm，比層高小一個數量級——五秒的算術就能排除，卻差點讓我照著錯的原因去擴孔。
7. **設計文件寫的理由，要標記它是量過的還是推論的。** vu1 細頸的「聲學隔離」被當成既定事實寫在 260721 README 裡，實際從未量過；查了 F11 與 GRAVEYARD 才確認可以放棄。**推論寫成結論，下一個人就不敢動它。**
8. **不要把承重的東西命名為 `TMP_`。** 四個 sketch 是 jhook 與 vu1 幾何的來源，卻頂著看起來可刪的名字；哪天照名字清理就是連鎖刪除。
